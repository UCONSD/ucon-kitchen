# DECISIONS.md — UCON Kitchen

Architectural decision log. One row per decision. Copy final entries here at release
(Phase 5). Keep the four columns.

| Date | Decision | Why | Alternatives rejected |
|------|----------|-----|-----------------------|
| 2026-08-10 | New app **UCON Kitchen** is a fully separate project — its own repo (`UCONSD/ucon-kitchen`), Supabase project, Vercel project, and domain (`project.ucon.us`), isolated from the UCON Field App | App is autonomous from the Field App; isolation gives zero blast radius on live field data and never opens the Field App's data rules when this app changes | Sharing the Field App's backend ("one warehouse, two doors") — rejected: the apps do not share data, and a shared backend would make every change a FULL-mode risk to live field data |
| 2026-08-10 | **Schema-first, event-sourced foundation.** Design Project State + milestones + append-only events + rules engine before building the conversational AI. AI emits events; a deterministic engine computes milestone transitions | The chat must not be the source of truth, or you get a smart conversation on top of a dumb system. Matches the accumulation-first principle | Chat-first (LLM writes state/transitions directly) — rejected as fragile, non-auditable, and impossible to reason about |
| 2026-08-10 | **Data stack = Supabase (PostgreSQL) + Supabase Auth + Supabase Storage**, not Firebase | The product is fundamentally relational + analytical: structured Project State, per-fact provenance metadata, funnel analytics, a designer dashboard. Postgres fits this far better than Firestore's document model. Supabase mirrors Firebase's Auth/Storage/hosting model closely, so the learning curve is modest. "Reuse" is honored at the account + workflow level | Reusing Firebase/Firestore from the Field App — rejected: Firestore's NoSQL document model fights the relational and analytical core of this app. Would have been chosen only if "learn nothing new" outranked fit |
| 2026-08-10 | Frontend **Next.js + React + TypeScript**; **OpenAI Responses API** for AI; **Vercel AI SDK** for streaming/UI only — no business logic inside the SDK; **PostHog** for funnel analytics; **Stripe** deferred until paid milestones | Matches the product handoff brief (§32); keeps business-critical logic in the rules engine and out of the model/SDK | Putting orchestration/business rules inside the AI SDK — rejected: business-critical state transitions must be deterministic and testable |
| 2026-08-10 | **Modular monolith**, not microservices, with clean internal boundaries (conversation / project state / qualification / rules / files / human review / analytics) | Right size for MVP and a solo developer; boundaries allow later extraction into services if volume justifies it | Microservices — rejected as premature complexity for pre-validation MVP |
